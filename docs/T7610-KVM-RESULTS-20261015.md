## Inference (steps 4 and 5)

llama-server command: `results/.../llama-server-command.txt` (`-ngl 0 -t 2 -tb 2 -b 128 -ub 32 -c 4096 --cache-ram 128 --reasoning off -n 128`, same as the guide).
Model start to health: 14 s and 15 s (the TCG guest needed about 100 s).

| Prompt | Cold 1 wall | Warm wall | Cold 2 wall | Prompt tok/s (cold) | Gen tok/s (cold) | TCG wall (earlier) |
|---|---:|---:|---:|---:|---:|---:|
| `Reply with the single word OK.` | 12.1 s | 2.2 s | 15.5 s | 1.3 | 2.1 | 9.0 s (cache already warm) |
| Python `add(a, b)`, code only | 37.5 s | 22.1 s | 43.1 s | 1.3 | 0.8 to 1.1 | 125.6 s |
| `What is 7 plus 5?` number only | 19.9 s | 3.0 s | 19.6 s | 1.3 | 1.5 to 1.6 | 79.4 s |
| Whole script | 71 s | 27 s | 79 s | | | about 214 s |

Prompt processing is about 1.3 tokens/s and generation 1 to 2 tokens/s with the
SSE2 baseline build. KVM is roughly 3 times faster than the TCG baseline on
these controls. The TCG cache states differed, so this is a platform
comparison, not a clean speed-up ratio. The host was shared with a running LLM
service and other jobs (host load average 4 to 8 of 24 threads); no pinning was used.

OpenCode through the TUI was much slower than these controls: the first exchange
(`Reply with OK only.`) took **15 m 51 s** (TCG: 15 m 41 s). The request carries
OpenCode's system prompt: 530 tokens processed in 720.9 s (**0.74 tok/s**),
then 2 tokens. The same 530-token prompt rate is lower than the direct 1.3 tok/s,
and the cause is not established (contention on the shared host and
guest services are plausible). Follow-ups reuse the cached prefix and took
45 to 52 s. The `-b 128 -ub 32` profile was tuned for TCG and is likely too small for
KVM; try larger batches before judging throughput.

The daemon itself created the terminal, so the failure is only in the renderer |
| Same pane with `reference/opentui-haiku-ghostty-vt.patch` (`.haiku => true`) | **Passes in a manual test, experimental.** The renderer builds (22.3 MB against 17.2 MB). In a copy of the install: split pane with `bash`, command I/O, UTF-8, pane size, **reconnect after quitting and restarting the TUI** (previous output returned), `exit 3` in the pane closes the pane without a crash, no leftover terminal or shell. Not in the archive, not applied by `build_native.sh` |
| Browser GUI terminal panel rendering | **Not tested visually.** Only the legacy PTY API path is covered |

Operational traps found: the TUI remembers the selected terminal per session
(`state/opencode/haiku/tui/session-terminal-selection.json`), so after the
failed pane **every restore of that session crashes** until the terminal is
deleted (`DELETE /api/experimental/persistent-pty/ID`) and the entry is reset.
Pane focus keys are leader (Ctrl-X) then Left, Right, Up (close). With the pane
focused, keystrokes go to its shell, not the TUI. Unframed WebSocket input
re-applies the size from attach time; clients must use `input_protocol=1`.

## Step 8: coding fixture

Fixture and runner: `tools/tui-port/coding-workflow.mjs` (unchanged apart from
upload names in a copy), tools enabled, four agent steps, 4096 context, 256
response tokens, deny-all permission list with narrow read, edit and shell
rules, 45-minute bound. Evidence: `coding-outcome.json`, `coding-agent-model.log`,
`coding-progress.log`.

- Prompt of 1,426 tokens took about 28 minutes (0.6 to 0.8 tok/s); the three later steps used 12, 65 and 68 new prompt tokens plus 223 in the last.
- Tool calls: `read add.mjs`, `edit add.mjs` (`a - b` to `a + b`, one replacement), `write add.mjs` (same content). No `shell` call, so the runner reports `semantic_pass: false`. The last step returned only an empty think block.
- `add.mjs` ends as `export const add = (a, b) => a + b;` and `node test.mjs` prints `AGENT_TEST_PASS`; `test.mjs` was not changed.
- Generation during this run was 0.4 to 0.6 tok/s and prompt processing 0.63 to 0.76 tok/s, lower than in the direct controls (1.3 and 1 to 2 tok/s). The OpenCode servers and Node processes were running alongside the model on the 2 vCPUs. This is a model-quality and throughput observation, not a transport or tool failure; one run proves nothing about reliability.

## Errata and deviations against the guide

1. Linux host Python 3.10 cannot extract the OpenCode source with `tarfile` filter `data` (symlinks are misjudged); use GNU `tar -xzf`. The guide says Python 3.12+.
2. The Haiku nightly installer leaves the new EFI system partition empty; copy `EFI/BOOT/BOOTX64.EFI` from the live ISO's ESP (KVM-VM.md).
3. `cargo build` of the daemon failed once while llama.cpp was compiling: `failed to build archive ... Bad address (os error -2147478783)`. A rerun with nothing else running succeeded. Do not overlap Cargo with another large build.
4. Pinned PTY daemon is 0.2.0 at `878aa26...` (`PTY-PORT-INPUTS.json`); `CONTINUATION-INPUTS.json` lists 0.3.1 (`443945a...`) as inspected only.
5. Rebuilt hashes differ from the recorded ones for the Haiku SDK, Koffi addon, Ghostty parser and native renderer (above). The recorded files were updated or annotated; none of the checks was disabled.
6. `inference-compare.cjs` uploaded to a fixed result name; it takes an optional fourth argument for the upload name now.
7. Stray WebPositive console messages (`ResizeObserver loop...`) appear in the Terminal that launched it.
8. A Haiku screen blanker blanks the console after several minutes: press a key.
